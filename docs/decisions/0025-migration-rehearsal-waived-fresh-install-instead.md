# 0025 — The migration rehearsal is waived; the fresh-install path is verified instead

Date: 2026-10-30
Status: accepted
Supersedes the Phase 12 gate described in `UNIBAAZAR_V2_MASTER_PLAN.md`
and in `docs/launch-checklist.md` §1.

## Context

The master plan closes Phase 12 with a data-migration rehearsal: take a
`mysqldump` of production, restore it into a scratch schema, run the
migrations against it, and prove nothing was lost — row counts,
`SUM(total)`, the oldest and newest orders still resolving their items
and payment history, every `Payment.status` landing cleanly on Phase 7's
8-state enum. `docs/post-launch-plan.md` carried it as Phase 14 and
marked it blocked on the human producing a dump.

Two facts from the human changed what that gate is for:

1. **The production database holds only demo/test data.** There are no
   real customer orders, no real payment history, no PII.
2. **v1 is not being migrated. It is being replaced.** The plan is to
   delete the existing deployment outright and install v2 fresh from a
   clean `git clone`.

The rehearsal exists to answer one question: _will applying these
migrations to the real data lose or corrupt any of it?_ With no real
data, and with the old installation being deleted rather than upgraded,
that question has no content. Restoring a dump of demo rows and
counting them afterwards would produce a green report that proves
nothing about launch.

What the rehearsal _would_ also have done, incidentally, is run the
deploy pipeline for the first time. That part is not ceremony — deploys
have been deliberately manual and deferred since ADR 0007, so no part of
`ci.yml` → `deploy.yml` → `deploy-release.sh` had ever executed end to
end.

## Decision

Waive the data-integrity rehearsal. In its place, verify the path that
will actually be used — a first deploy onto an empty database — and fix
what that verification turns up.

Three first-deploy-only defects were found and fixed this way:

- **The release tarball omitted `scripts/`.** `deploy.yml`'s final step
  is `bash "$APP_PATH/releases/$SHA/scripts/deploy/deploy-release.sh"`,
  and that script in turn calls `backup-db.mjs` and
  `apply-migrations.sh`. The first real deploy would have failed on its
  first command.
- **`--exclude='.next/cache'` was written after the path list**, where
  tar treats it as positional and it matched nothing. Every release
  carried 710MB of webpack cache; locally that invocation also exits
  non-zero, so depending on the runner's tar version the packaging step
  either shipped ~718MB or failed outright.
- **`apply-migrations.sh` could not parse a DB password containing
  symbols** — it split credentials on the first `@` and never decoded
  percent-escapes. A password generated by cPanel, which is exactly what
  a fresh install produces, broke it both ways.

None of the three was reachable without actually exercising the
pipeline, and none would have been caught by restoring a dump.

## Consequences

- **Phase 12's gate closes on this ADR plus `docs/qa/phase-14-report.md`,
  not on an approved rehearsal.** The deviation is deliberate and
  recorded here so the master plan and the code don't silently disagree.
- **The waiver is void if the premise is.** It rests entirely on the
  production database holding nothing real. If anything in it turns out
  to matter, the rehearsal in `docs/launch-checklist.md`'s git history
  is the procedure to run before touching it.
- **A pre-wipe dump is still taken** — not as a rehearsal input, but as
  the only way back if the premise is wrong. It must never reach git;
  `.gitignore` now blocks `*.sql`, `*.sql.gz` and `*.dump` outside
  `prisma/migrations/`.
- **`shared/uploads` is not in the repo and not in the release.**
  Deleting the old installation deletes every product image that was
  ever uploaded through the admin. They have to be copied off the host
  first or re-uploaded afterwards; `docs/launch-checklist.md` §1 now
  says so as a blocking step.
- **The first deploy has no rollback target.** `deploy-release.sh`
  handles this correctly — it reports `<none, this was the first
deploy>` rather than failing — but it means the pre-wipe dump plus the
  image copy are the entire recovery plan for deploy #1.
- **The shell parsing in `apply-migrations.sh` has no automated test.**
  The repo has no harness for shell scripts, and adding one for a single
  parser is not worth a new tool in the toolchain mid-launch. It was
  verified behaviourally against plain, raw-`@`, percent-encoded,
  no-port and mixed `%23`/`%25`/`%3A` passwords, and the reasoning is in
  the script's own comments. Noted as debt in Phase 18.
